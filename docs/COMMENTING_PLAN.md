# 教科書形式コメントの方針と実施状況

この文書は、HTML・CSS・JavaScriptへ初心者向けコメントを残すときの共通ルールを定める。初回のコメント追加は実施済みで、今後の改修でも同じ基準を維持する。

## 目的

- 初めてWeb制作を見る人でも、ファイルの役割と処理の流れを順番に追えるようにする。
- 「何をしているか」だけでなく、「なぜ必要か」「入力と出力は何か」「失敗するとどうなるか」を説明する。
- コメントを読めば、修正箇所の候補と確認方法を判断できるようにする。

## 共通ルール

1. 専門用語を初めて使う場所で短く説明する。
2. コードを日本語へ逐語訳せず、その処理が必要な理由を書く。
3. まとまりの先頭に章コメントを置き、細かな行コメントは誤解しやすい箇所だけにする。
4. 関数には「目的・入力・出力・画面や保存への影響・失敗時」を必要に応じて書く。
5. 正規表現には、認識する原稿例と認識しない例を最低1つずつ付ける。
6. TALTO、Obsidian、HTMLの仕様による判断には、参照元とこのツール固有の変換方針を分けて書く。
7. セキュリティ上除外するHTML要素には、除外理由を書く。
8. CSSは「対象部品・見た目の目的・PC／スマホでの違い」を章コメントで説明する。
9. HTMLは、主要な領域の開始と終了、アクセシビリティ属性の目的を説明する。
10. コメント追加後も、通常テストとランダムテストの結果が変わらないことを確認する。

## 関数コメントのひな型

```js
/**
 * 目的:
 *   この関数が利用者のどの操作を支えるか。
 *
 * 入力:
 *   引数が表すものと、想定する値。
 *
 * 出力:
 *   戻り値の内容。戻り値がなければ、その旨を書く。
 *
 * 影響:
 *   画面、設定、クリップボード、ファイル一覧など、変更する状態。
 *
 * 注意:
 *   例外、上限、意図的に対応しない形式。
 */
```

短い補助関数では全項目を埋めず、1〜3行の説明に縮める。コメントの量ではなく、初学者が処理の理由を追えることを完成条件にする。

## 初回実施時の作業順

1. `converter.js`へ章コメントと変換例を追加する。
2. 変換テストを実行し、コメントだけの差分であることを確認する。
3. `app.js`（旧 `helper.js`）へ状態とイベントの流れを追加する。
4. `app.css`（旧 `helper.css`）へ部品単位の章コメントを追加する。
5. HTMLへ画面構造とアクセシビリティの説明を追加する。
6. READMEのファイル説明と実際の構成を照合する。
7. 改修デバッグ版を再生成し、フォルダ構造と起動を確認する。

## 完成条件

- 各ファイルの冒頭だけで、そのファイルの役割が分かる。
- 長い関数は目的と副作用を確認してから読める。
- 正規表現に具体例がある。
- HTML・CSS・JavaScriptのつながりをREADMEから追える。
- コメントを削除しても動作が変わらない。
- コメント追加前後で全テストが同じ結果になる。

## 現在の状態

- HTMLには、ホーム、4工程、スマホ操作、スクリプト読込順の章コメントを追加済み。
- CSSには、色、画面構造、入力、設定、プレビュー、ダークモード、画面幅の章コメントを追加済み。
- `app.js`と`converter.js`は、主要な全関数に目的と安全上の理由を追加済み。
- 形式カタログ、テスト、ローカルサーバー、配布処理にも役割説明を追加済み。
- コメント追加後は構文検査、通常テスト、構造テスト、ランダムテストを実行する。
