# クロスプラットフォーム計画書のレビュー

対象: `CROSS_PLATFORM_BOOTH_RELEASE_PLAN.md`（2026-09-16 初版）
レビュー日: 2026-09-16
結論: **方向性・非目標・受け入れ基準は採用。ただし「モバイルは HTTPS 版が標準」という前提を「完全オフライン動作」へ差し替え、未決事項3点を確定したうえで改訂版へ置き換える。**

改訂版は同じファイル名で上書きした。このレビューは「なぜそう変えたか」の記録として残す。

## 1. 確定した事項（初版で未決だったもの）

| 事項 | 決定 | 理由 |
|---|---|---|
| 目標 | **完全オフライン動作**を Windows・iOS・Android すべてで目指す | 制作者の意向。原稿の非送信（実装済み）とは別に「ネット接続なしで起動できる」を目標に加える |
| モバイルの配布経路 | **PWA を主経路、単一ファイル HTML を予備経路** | iOS は ZIP 内の HTML を直接開く方法で動作保証できない（後述 3-2）。PWA なら初回だけ HTTPS で開けば以降はオフラインで動く |
| ホスティング先 | **GitHub Pages** | 無料・カード登録不要・広告や解析の差し込みなし。サーバーを持たないため保守作業が発生しない |
| ライセンス | **MIT** | ソース同梱で配布する現行方針と整合。Web 公開分も同じ条件 |
| ブラウザ自動テスト | **Playwright を開発用依存として追加** | 代表幅の横スクロール検査・PWA のオフライン起動確認を自動化する。ツール本体・ZIP 版のテストは引き続き Node のみで動く |
| git の範囲 | **`migration-helper-v2/` をリポジトリのルートにする** | 作業フォルダ直下には TALTO の復元コード（`app/` `vendor/`）と個人の通信記録（`project-capture/`）があり、公開リポジトリに含めてはいけない |

## 2. 初版の良い点（維持する）

- 非目標が明確。原稿の外部送信なし、非公開 API 不使用、貼り付け・画像挿入は手作業。これらは現行コードでも守られている（`app.js` に `fetch` / `XMLHttpRequest` は存在しない。localStorage に入るのは設定とテーマのみ）。
- Windows を基準環境として固定し、後退させないことを公開条件の第1項に置いている。
- Blocker / Major / Minor の区分と、v1.0.0 公開判定の9条件が具体的。
- 実機でしか確認できない項目（OS のファイル選択、リッチテキストコピー、ソフトウェアキーボード、画面回転）を明示している。
- 「不具合報告に原稿本文の添付を求めない」という保守方針は、個人の原稿を扱うツールとして正しい。

## 3. 初版の問題点と修正内容

### 3-1. 前提のズレ: 「モバイルは HTTPS 配信版を標準経路」

初版は「モバイルは Web 版を開く」前提で、オフライン動作を要件にしていない。制作者の目標は完全オフラインなので、次のように改める。

- Windows: ZIP 展開 → HTML 直開き（現行どおり、最初から完全オフライン）。
- iOS / Android: 初回だけ HTTPS 版を開き、**ホーム画面に追加**する。Service Worker が全ファイルをキャッシュし、以降は機内モードでも起動する。
- 予備経路: CSS / JS をすべて埋め込んだ**単一ファイル HTML** を ZIP に同梱する。Android の一部環境ではこれを直接開ける。iOS では動作保証しない。

「原稿を送信しない」と「ネットなしで起動できる」は別の要件なので、改訂版では書き分けた。

### 3-2. iOS でローカル HTML を直接開けない理由（計画書に根拠がなかった）

- Files アプリで `.html` をタップすると Quick Look プレビューになり、通常の Safari とは別の制限付き環境で表示される。`src/` へ分割したファイルの読込、`navigator.clipboard`、`<input type="file">` が期待どおり動かない。
- Safari には `file://` を直接開く UI がない。
- したがって iOS で正式対応するには HTTPS 経由で一度読み込ませる以外に現実的な方法がない。PWA を主経路にするのはこの制約による。

### 3-3. 「広告を追加しない構成」の一文

これは「無料ホスティングの中には広告や解析スクリプトを勝手に差し込むものがあるので避ける」という注意書きだった。GitHub Pages に確定したので、この一文は不要になり削除した。代わりに「ホスティング先が差し込むスクリプトがないこと」を Phase 1 の確認項目に残す。

### 3-4. Phase 2 の見積りが過大

「スマートフォンは工程ごとに1画面ずつ表示」は**すでに実装済み**。

- `app.css:361` で 760px 以下のとき `data-step` に応じてカードを切り替えている。
- `app.css:385` の `.mobile-action` が固定の次工程ボタンで、`env(safe-area-inset-bottom)` も考慮済み。
- `app.js:534` の `setStep()` が工程遷移とスクロール位置のリセットを担っている。

未着手なのは iPad 縦向き・Split View の1カラム化、ソフトウェアキーボード表示時の固定ボタン退避、文字サイズ拡大への追従。改訂版では Phase 2 を「既存の工程表示を iPad と入力中に拡張する」に縮小した。

### 3-5. Phase 3 のクリップボード

現行は `ClipboardItem` → 失敗時 `execCommand("copy")` の2段構え（`app.js:891-905`）。計画書の要求と現状の差:

- 失敗理由（API 非対応 / 権限拒否 / 書込失敗）を区別せず、すべて同じ `catch` で予備処理へ落としている。
- iOS Safari では、隠し contentEditable への `execCommand("copy")` が効かないことが多い。計画書にある「選択可能なコピー領域と長押しコピー」は iOS 対応の必須項目であり、「予備」ではなく**iOS の第2正式経路**として扱う。
- `navigator.clipboard.write` は iOS Safari でユーザー操作の同期文脈内でしか成功しない。現行は `convert(true)` が同期なので問題ないが、将来 `await` を挟むと壊れる。改訂版の Phase 3 に「ボタン押下から `write()` 呼出しまでに `await` を入れない」を制約として明記した。

### 3-6. Phase 4 の `webkitdirectory` 検出

`"webkitdirectory" in input` は iOS Safari でも `true` を返すが、実際のファイル選択画面にフォルダを選ぶ手段がない。プロパティの有無で判定すると「フォルダを追加」が表示されるのに何も選べない状態になる。

改訂版: タッチ主体の端末（`navigator.maxTouchPoints > 1` かつ `(pointer: coarse)`）では「複数ファイルを追加」を主経路として前に出し、フォルダ追加は「PC 向け」と表示して後ろに下げる。判定は表示順の変更だけに使い、機能自体は無効化しない。

### 3-7. Phase 6 のブラウザテストに道具の指定がなかった

「代表幅で横オーバーフローを検査」は Node だけでは不可能。Playwright を追加することに決めたので、次を切り分けた。

- `tests/`: 従来どおり Node のみ。ZIP に同梱し、受け取った人が `npm` なしで実行できる。
- `e2e/`: Playwright。`package.json` の開発用依存。ZIP には同梱しない。
- Windows の Chromium と、iOS 相当として WebKit を実行対象にする（実機の代替にはならないが、iOS 特有の失敗をローカルで先に拾える）。

### 3-8. 権利面の確認項目が「非公式表記」だけだった

変換仕様の根拠は talto.cc のソースマップから復元したフロントエンドコードにある。改訂版で次を追加した。

- 公開リポジトリと配布物には `migration-helper-v2/` の内容だけを含める。復元コード・HAR 由来データは対象外。
- `docs/MIGRATION_GUIDE.md` の「解析根拠」は復元コードのファイルパスを引用している。コード自体は含まれないが、公開前に表現を「TALTO のエディタ挙動の観察結果」へ改めるかどうかは制作者が判断する。改訂版では Phase 8 の確認項目として残した。
- 配布物の自動検査に「`app/` `vendor/` `project-capture/` 由来のファイルが混入していないこと」を追加する。

### 3-9. Web 版と ZIP 版の同期手段がなかった

Phase 9 に「バージョンを一致させる」とあるが仕組みがない。改訂版:

- `VERSION.txt` を単一の情報源とし、ビルドツールが HTML の表示・`manifest.webmanifest`・Service Worker のキャッシュ名・ZIP 名へ展開する。
- ZIP と Web 版（`dist/`）は同じ `tools/build-release.mjs` から同時に生成する。片方だけ更新できないようにする。

### 3-10. PWA 特有の保守事項が書かれていなかった

Service Worker はキャッシュが古いままになると「直したはずのバグが利用者側で直っていない」が起きる。これは運用の手間ではなく実装時の設計で解決する。

- キャッシュ名にバージョンを含め、新バージョンの SW が有効化された時点で旧キャッシュを削除する。
- 画面に「新しい版があります。再読み込みしてください」を出す。
- iOS Safari はホーム画面に追加していないサイトのストレージを一定期間の未使用後に消すことがある。オフライン利用の案内では「ホーム画面に追加」を必須手順にする。

### 3-11. 細かい修正

- 「対応環境.md」「既知の問題.md」の2文書は初版の Phase 8 にだけ現れる。Phase 0 で作り始めるよう前倒しした。
- 実装優先順位（8項目）と Phase（10段階）の対応を表にした。
- `LICENSE.txt` の内容が未定だった → MIT に確定。
- git リポジトリの作成、GitHub アカウント、Pages の有効化は制作者の作業として Phase 0 に明記した。

## 5. 着手前に制作者が行うこと

Claude 側では代行できない作業。

1. GitHub アカウントを用意する（未作成の場合）。
2. `migration-helper-v2/` を**公開**リポジトリとして GitHub に作る。リポジトリ名は Pages の URL になる（例: `talto-migration-helper` → `https://<ユーザー名>.github.io/talto-migration-helper/`）。
3. リポジトリの Settings → Pages で、配信元を「GitHub Actions」にする。
4. 初回コミットとプッシュを行う。

git のユーザー名とメールアドレスが未設定なので、初回コミット前に設定が必要（改訂版 Phase 0 にコマンドを記載）。
